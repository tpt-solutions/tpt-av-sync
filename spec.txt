# tpt-av-sync

**A pure-Rust, CRDT-based real-time collaboration engine for media timelines. Multi-user editing, playhead synchronization, and conflict-free state replication. The collaboration layer of the TPT AV stack.**

**License:** MIT  
**Status:** Early-stage / Pre-1.0  
**Ecosystem:** [TPT Solutions Open Source](https://opensource.tptsolutions.co.nz/)

---

## 1. Vision & Philosophy

`tpt-av-sync` is the **real-time collaboration layer** of the TPT AV Stack. It enables multiple users to edit the same audio or video timeline simultaneously, with automatic conflict resolution and real-time synchronization of edits, playhead positions, and parameter changes.

The current landscape of collaborative media editing is limited:
- **Proprietary solutions:** Frame.io, Descript, and a few cloud-based tools offer basic collaboration, but they are closed-source and expensive.
- **Legacy DAWs:** Pro Tools, Logic, and Ableton have no real-time collaboration. They rely on file-based workflows (send project → receive project).
- **General CRDTs:** Libraries like `automerge` and `y-crdt` provide generic conflict-free data structures, but they are not optimized for media timelines with complex spatial-temporal relationships.

`tpt-av-sync` fills this gap by providing:
1. **Media-specific CRDTs** — conflict-free data structures designed for timeline operations (clip insert, move, delete, split, trim)
2. **Real-time playhead synchronization** — sub-millisecond precision across network connections
3. **Operational transforms** — handle concurrent edits from multiple users without conflicts
4. **Peer-to-peer architecture** — WebRTC data channels for low-latency, serverless collaboration
5. **Offline-first design** — edits work offline and sync when reconnected
6. **Pure MIT licensing** — zero copyleft contamination

### Core Tenets

1. **Conflict-Free by Design:** All timeline operations are commutative and idempotent. No matter what order operations arrive, the final state is identical across all peers.
2. **Real-Time Safe:** Playhead synchronization and parameter updates are allocation-free and lock-free. Safe to call from audio/render threads.
3. **Offline-First:** All edits are stored locally and synced when network is available. No data loss during disconnections.
4. **Pure Rust, Zero External Sync Dependencies:** No C/C++ bindings. CRDT implementation is pure Rust.
5. **Peer-to-Peer Architecture:** Uses WebRTC data channels for direct peer-to-peer communication. No central server required (but server-based relay is supported).
6. **Pure MIT Licensing:** No GPL/LGPL/MPL dependencies. Enforced via `cargo-deny` in CI.
7. **Composable Architecture:** Each sub-crate is independently useful. A developer can use just the CRDT engine, just the network layer, or just the playhead sync.

## 2. Ecosystem Integration

`tpt-av-sync` sits in the **Collaboration Layer** of the TPT AV Stack, working alongside `tpt-audio` and `tpt-visual` to enable multi-user editing.

| Crate | Role | Relationship to `tpt-av-sync` |
| :--- | :--- | :--- |
| **`tpt-audio`** | Audio timeline, processing | `tpt-av-sync` replicates audio timeline state across peers. |
| **`tpt-visual`** | Video timeline, compositing | `tpt-av-sync` replicates video timeline state across peers. |
| **`tpt-av-sync`** | **Collaboration (this repo)** | CRDT engine, network sync, playhead synchronization. |
| **External Peers** | Other users' applications | Send/receive timeline operations via WebRTC/WebSockets. |

### Data Flow
User A makes edit (e.g., moves clip)
↓
tpt-av-sync-crdt creates operation (ClipMove { clip_id, new_position })
↓
tpt-av-sync-net sends operation to peers (WebRTC data channel)
↓
User B receives operation
↓
tpt-av-sync-crdt applies operation to local timeline
↓
tpt-audio / tpt-visual updates UI

4. Core API Design
4.1. CRDT Operations (tpt-av-sync-crdt)

/// A timeline operation that can be replicated across peers.
///
/// All operations are commutative and idempotent.
/// No matter what order they arrive, the final state is identical.
#[derive(Debug, Clone)]
pub enum TimelineOperation {
    /// Insert a new clip into a track.
    InsertClip {
        /// Unique clip ID (generated by the peer creating the clip).
        clip_id: ClipId,
        /// Target track ID.
        track_id: TrackId,
        /// Clip data.
        clip: ClipData,
        /// Position in the track (index).
        position: usize,
    },
    
    /// Move a clip to a new position.
    MoveClip {
        /// Clip ID.
        clip_id: ClipId,
        /// New track ID (can be same track).
        new_track_id: TrackId,
        /// New start time (in frames/samples).
        new_start_frame: u64,
        /// New position in the track.
        new_position: usize,
    },
    
    /// Delete a clip.
    DeleteClip {
        /// Clip ID.
        clip_id: ClipId,
    },
    
    /// Split a clip at a specific time.
    SplitClip {
        /// Original clip ID.
        clip_id: ClipId,
        /// Split time (in frames/samples, relative to clip start).
        split_frame: u64,
        /// ID for the new clip (right half).
        new_clip_id: ClipId,
    },
    
    /// Trim a clip (change duration).
    TrimClip {
        /// Clip ID.
        clip_id: ClipId,
        /// New duration (in frames/samples).
        new_duration: u64,
        /// Which edge is being trimmed.
        edge: TrimEdge,
    },
    
    /// Update clip metadata (name, color, etc.).
    UpdateClipMetadata {
        /// Clip ID.
        clip_id: ClipId,
        /// Metadata updates.
        updates: ClipMetadataUpdate,
    },
    
    /// Insert a new track.
    InsertTrack {
        /// Track ID.
        track_id: TrackId,
        /// Track data.
        track: TrackData,
        /// Position in the session.
        position: usize,
    },
    
    /// Delete a track.
    DeleteTrack {
        /// Track ID.
        track_id: TrackId,
    },
    
    /// Update an automation envelope.
    UpdateEnvelope {
        /// Clip ID (or track ID for track-level envelope).
        target_id: TargetId,
        /// Envelope type (volume, pan, custom).
        envelope_type: EnvelopeType,
        /// Envelope points.
        points: Vec<EnvelopePoint>,
    },
    
    /// Update session metadata (name, sample rate, etc.).
    UpdateSessionMetadata {
        /// Metadata updates.
        updates: SessionMetadataUpdate,
    },
}

    /// Timestamp (wall clock, for display only).

}

4.2. Network Transport (tpt-av-sync-net)

/// Network transport trait.
pub trait Transport: Send + Sync {
    /// Sends a message to a specific peer.
    fn send_to(&mut self, peer_id: PeerId, message: SyncMessage) -> Result<(), SyncError>;

    /// Broadcasts a message to all peers.
    fn broadcast(&mut self, message: SyncMessage) -> Result<(), SyncError>;

    /// Receives the next message (blocking).
    fn recv(&mut self) -> Result<(PeerId, SyncMessage), SyncError>;

    /// Receives the next message (non-blocking).
    fn try_recv(&mut self) -> Result<Option<(PeerId, SyncMessage)>, SyncError>;

    /// Returns the list of connected peers.
    fn peers(&self) -> Vec<PeerId>;
}

/// Network messages.

    /// Acknowledgment of received operation.

}

5. Conflict Resolution Strategy
5.1. Commutative Operations
All timeline operations are designed to be commutative (order doesn't matter) and idempotent (applying the same operation twice has no additional effect).
Example: Concurrent Clip Moves

User A moves Clip X to position 100
User B moves Clip X to position 200

Both operations arrive at User C.

Resolution: Last-writer-wins based on Lamport timestamp.
If A's operation has higher timestamp, final position = 100.
If B's operation has higher timestamp, final position = 200.

Example: Concurrent Clip Deletes

User A deletes Clip X
User B deletes Clip X

Both operations arrive at User C.

Resolution: Idempotent. Clip X is deleted once.

Example: Concurrent Clip Splits

User A splits Clip X at frame 500
User B splits Clip X at frame 1000

Both operations arrive at User C.

Resolution: Both splits are applied. Clip X becomes three clips:
- Original (0-500)
- Middle (500-1000)
- Right (1000-end)

5.2. Vector Clocks for Causal Ordering
Vector clocks track causality between operations:

/// A vector clock for tracking causal relationships.
#[derive(Debug, Clone)]
pub struct VectorClock {
    /// Clock values for each peer.
    clocks: HashMap<PeerId, u64>,
}

impl VectorClock {
    /// Increments the clock for a specific peer.
    pub fn increment(&mut self, peer_id: PeerId);

    /// Merges another vector clock (takes max for each peer).
    pub fn merge(&mut self, other: &VectorClock);

    /// Returns true if this clock is causally before another.
    pub fn happens_before(&self, other: &VectorClock) -> bool;

    /// Returns true if this clock is concurrent with another.
    pub fn is_concurrent(&self, other: &VectorClock) -> bool;
}

6. Network Architecture
6.1. Peer-to-Peer with WebRTC

User A (Browser/Desktop App)
        ↓ WebRTC Data Channel
User B (Browser/Desktop App)
        ↓ WebRTC Data Channel
User C (Browser/Desktop App)

All peers are directly connected.
No central server required.

6.2. Signaling Server (Optional)
For peers behind NAT or firewalls, a signaling server helps establish WebRTC connections:

User A → Signaling Server → User B
         (exchange SDP offers/answers)
         (exchange ICE candidates)

After connection established:
User A ←→ User B (direct peer-to-peer)

6.3. Relay Server (Fallback)
If peer-to-peer fails, messages can be relayed through a server:

User A → Relay Server → User B
